nxm-mcp-session — how it works

Long image

A

Answer

nxm-mcp-session turns a long, noisy coding session into a standard handoff document and keeps a session registry, so a fresh agent resumes the work without losing quality — and it is a thin binary over a shared, config-agnostic core.

  1. A long session degrades the model; a structured, forward-looking handoff lets the next session restart cleanly.
  2. It is harness-agnostic: any MCP client (Kiro, Pi, Codex, Claude) drives it over JSON-RPC on stdio.
  3. All session logic lives in nxm-session-core; the binary only resolves config/env and wires logging.
  4. 14 typed tools: pure read/state, three transport-driven (Sampling/Elicitation), lifecycle, archive and a cross-repo registry.

What it is

A small, dependency-light MCP server. It does not watch your conversation and does not run in the background: it is reactive. A client calls a tool, the server acts and returns structured JSON. Context isolation is by design: the server never sees the conversation, so synthesis runs through the client's own model via MCP Sampling.

How is the binary put together?

Diagram structure
  • MCP Client client
  • nxm-mcp-session binary
  • wiring.rs wiring
  • nxm-session-core core
  • sessions/ local
  • ~/nxm/sessions global
  • client → binary · stdio
  • binary → wiring · resolve
  • wiring → core · inject structs
  • core → local · handoffs
  • core → global · pointers

The binary owns config/env resolution and logging; it injects already-resolved values into the core, which reads no environment at all.

  1. MCP Client ↗

    Any harness drives the server over JSON-RPC on stdio.

  2. nxm-mcp-session ↗

    Captures HOME/PWD/session id, sets up logging via nxm-shared.

  3. wiring.rs ↗

    Reads the [session] config and env, builds the injected structs.

  4. nxm-session-core ↗

    Receives final values — zero std::env — and runs all session logic.

How does a session move between states?

Five states, driven by set_status and reopen. done and superseded physically archive the handoff; done is terminal, superseded can be reopened.

StateMeaningReopen?
ActiveLive in the registry—
On HoldPaused in placeYes, in place
AbandonedDormant, stays in placeYes, in place
SupersededArchived, replaced by a successorrestores filesYes
DoneArchived, terminalcreate a successorNo

How does a fresh session resume?

  1. find_resumable_session

    At startup, ask for the best unconsumed handoff to resume.

  2. get_session

    Read the chosen handoff document in full before starting.

  3. mark_consumed

    Flip it to consumed so no one resumes it twice.

  4. generate_handoff

    When context fills up again, distil the new session.

6

Running it

Register it as an MCP server pointing at the installed binary. The product config lives at ~/.config/nxm/nxm-session.toml — the server reads it itself, whichever client launched it.
